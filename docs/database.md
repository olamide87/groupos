# Database foundation (GOS-002)

PostgreSQL 17 and Prisma 6.19.3 provide the persistence foundation. This change
adds no participant-facing endpoints, authentication, reminders or AI calls.

The root package overrides Prisma config's `deepmerge-ts` to patched 8.0.0 for
[GHSA-ggr8-5vv4-36mx](https://github.com/advisories/GHSA-ggr8-5vv4-36mx).
Schema validation, client generation and migration tests verify CLI compatibility.
Reassess this override when upgrading Prisma.

## Model and ownership

- `User` represents an organizer identity, with a unique normalized email. Future
  authentication work must add credential/session storage; there are no passwords
  in this model.
- Each `Event` belongs to one organizer. Every future organizer query and write
  must scope by both event ID and authenticated organizer ID. Foreign keys do not
  authenticate a caller, and database row-level security is not implemented here.
- `Participant` belongs to one event and does not require a user account. Email
  is optional; when present it is unique within that event. Application code must
  trim and lowercase email before writing; SQL checks enforce that convention.
- `InvitationToken` belongs to an event and optionally a specific participant.
  Its composite foreign key prevents linking a participant from another event.
- `Rsvp` holds one current answer per participant. `RsvpHistory` is the response
  history. Future RSVP handlers must update both in one transaction, as tested.
- `Poll` has a DATE, BUDGET or ACTIVITY kind. MVP options use display labels and
  explicit ordering. Each participant has one current vote per poll. Composite
  foreign keys enforce that voter and poll share an event and the chosen option
  belongs to that poll. Future handlers enforce poll status/closing times in the
  same transaction as writes. Structured date/currency options and multiple-choice
  voting are intentionally deferred.
- `Recommendation` records RULE or AI provenance, rationale and review status.
  PENDING is the default. Approval does not authorize automatic sending; future
  review actions must record the reviewer in the audit trail.
- `NotificationConsent` records the current email preference, provenance and
  update time. Absence means no consent; new rows default to OPTED_OUT. Future
  changes must append an audit entry in the same transaction and sending must
  recheck consent. No SMS or outbound delivery is implemented.
- `AuditEntry` records action, actor, entity and optional event, without arbitrary
  payloads that might accidentally capture tokens or contact details. Entity IDs
  are polymorphic references; actor and event have foreign keys. Participant
  actions may have no user actor. Application code must scope event/actor access.

UUID primary keys are generated by Prisma; direct SQL writers must supply IDs
and `updatedAt`. Timestamp columns are timezone-aware. Foreign-key indexes cover
event queries, votes, tokens and chronological histories. Deletion is RESTRICT
throughout so deleting an organizer/event cannot silently erase dependent data.

## Invitation security

Generate at least 32 random bytes for bearer tokens, send the raw value only in
the invitation, and store the lowercase SHA-256 hex digest. The database checks
the 64-character hash format and uniqueness; it cannot prove token entropy or
that a supplied string is actually hashed. Never log tokens or URLs containing
them. Resolve a token only when its hash matches, `revokedAt IS NULL`, and
`expiresAt > now()`. Expiry must follow creation and revocation cannot predate
creation. Expiry/revocation enforcement at request time belongs to GOS-005.

## Retention and operations

Contact details and preferences are personal data. Limit access to event owners
and the invited participant, avoid bulk disclosure, and use least-privilege
database roles and encrypted connections in hosted environments. Use a separate
migration role; the application role should not have DDL/CREATEDB privileges.
The local and CI test roles are deliberately privileged only for disposable tests.

Audit and RSVP history are append-only by application convention in this
foundation, not protected from a privileged database writer. Before production,
define and approve retention periods and deletion/anonymization procedures for
contact details, expired/revoked token hashes, events, response history, audit
records and backups. No unapproved retention period or automatic purge is added.
RESTRICT requires an explicit ordered cleanup/anonymization process. Restrict
history-table UPDATE/DELETE grants when provisioning runtime roles.

## Verification boundaries

The generated initial migration includes hand-reviewed CHECK constraints for
normalized emails, token format and temporal ordering, event dates and option
positions. The integration runner applies it to a newly created database, retries
deployment without changes, checks Prisma schema drift, and tests constraints,
transaction rollback and client reconnects. CHECK constraints are additionally
tested directly because Prisma's drift comparison does not model them.

This foundation does not establish authentication, API authorization, production
readiness or the full MVP definition of done. See the [setup guide](../README.md)
and [backlog](BACKLOG.md).
